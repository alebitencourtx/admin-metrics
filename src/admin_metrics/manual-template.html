01 / CONTEXTO E ESCOPO

Monitorar o que é observável.

Admin Metrics acompanha oito reportes operacionais Santander publicados via GET /open-banking/admin/v2/metrics. Combina métricas agregadas declaradas pelo banco com a medição independente da consulta ao próprio Admin.

Decisões apoiadas

Identificar concentração de erros, médias elevadas, rejeições, recorrência no histórico reportado, falhas de acesso e inconsistências de dados. Priorizar investigação com volume, instante e evidência.

Perímetro

Banco Santander, Toro, CCVM, Aymoré, Getnet, Hyundai e os reportes RCI Nissan/Renault. A associação é operacional pelo Diretório; não é atestado de controle societário. Não coletamos dados de clientes nem executamos pagamentos.

Duas latências distintas: duração Admin é o tempo observado da nossa tentativa HTTP; média declarada é o averageResponse informado pelo banco para o serviço. Nenhuma delas equivale a p95.

O projeto OpenData existente foi movido integralmente para observatory-opendata/. Este monitor está em admin-metrics/, com repositório e Pages independentes, para isolar publicação, agenda e estado. O plano foi escrito antes da implementação.

Um catálogo explícito e verificável.

O catálogo config/reporters.json é conferido contra o Diretório oficial de participantes. O comprovante em config/catalog-evidence.json registra instante, SHA-256, tamanho e correspondências de URL/CNPJ. O scheduler usa esse catálogo versionado; mudanças devem ser revisadas.

Contrato de entrada

Fonte técnica: OpenAPI oficial Admin 2.0.1. data[] contém endpoint, requestTime, availability e os objetos invocations, errors, rejections, averageResponse, averageTps, peakTps. Cada objeto temporal contém currentDay e previousDays, primeiro elemento referente a ontem, até sete posições.

A chamada envia period=ALL&page-size=1000&page=N. O total é conciliado por identidade de endpoint. Paginação repetida não aumenta tráfego: vence a primeira observação e valores divergentes são sinalizados. Cobrir totalRecords não comprova conformidade do metadata totalPages.

Integrações externas

  • Oito hosts HTTPS Santander: somente o caminho Admin; sem redirects e sem desativar TLS.
  • GitHub Actions: executa Python e publica artefato estático.
  • GitHub Releases: conserva dois pacotes operacionais aprovados; sem novos dados no histórico Git a cada ciclo.
  • GitHub Pages: entrega dashboard e documento na raiz do site.

O browser lê somente dados empacotados; não consulta APIs bancárias. Links externos são opcionais e explícitos.

03 / ARQUITETURA

Desenho de solução.

ETL em lote, single node, sem serviço de banco permanente. O runner é descartável: o estado é restaurado antes da coleta e persistido após publicação aprovada.

Deslize o diagrama lateralmente para ler todos os detalhes.

Bronze e estado

Respostas exatas por SHA-256; cada tentativa guarda HTTP, URL, duração, Date, bytes e erro. Histórico normalizado de 30 dias. Bronze empacotado apenas dos dois ciclos recentes.

Gold e consumo

Dados tipados Arrow materializados uma vez no DuckDB; agregações SQL e Parquet Zstandard. HTML real na raiz com assets imutáveis e documento único. Nenhum cluster é necessário nesta escala.

04 / FLUXO

Da agenda à publicação aprovada.

Deslize o diagrama lateralmente para ler todos os detalhes.

As tarefas compartilham o grupo de concurrency para impedir corrida entre coleta, estado e Pages. Retry é limitado a transporte e HTTP 408/429/500/502/503/504/529, até três tentativas, Retry-After limitado a 15 segundos. HTTP 403 é registrado sem tentativa de contornar bloqueio.

Limites: 4 reportes concorrentes, uma página por vez/reporte, 20 s de timeout por operação HTTP, 20 páginas por reporte, 16 MiB por resposta e 10.000 identidades por reporte. O workflow tem timeout; o ZIP de estado também tem limites de entrada, tamanho e expansão. Timeout de leitura é por operação, não prazo absoluto de toda a coleta.

Pages e Releases não formam uma transação distribuída. Se o deploy funcionar e a confirmação do estado falhar, o site poderá mostrar um run ainda em draft. Use o recibo/manifesto do candidato para recuperar; nunca faça fallback silencioso a um estado corrompido.

06 / REGRAS FUNCIONAIS

O diagnóstico é explicável.

Taxas, médias e amostras

  • Erro = 100 × errors / invocations; rejeição = 100 × rejections / invocations. Cada agregado usa só linhas com denominador positivo e numerador válido, menor ou igual às chamadas. Ausência não vira zero.
  • Média ponderada = Σ(averageResponse × invocations) / Σ(invocations), só para médias positivas e chamadas positivas. É uma aproximação agregada de médias declaradas; não recupera percentis nem corrige semântica da origem.
  • Erro ≥5% e ≥100 chamadas: atenção. Crítico requer erro ≥20% e ≥1.000 chamadas. Rejeição ≥5% com ≥100 chamadas: atenção. A interface mostra os volumes.
  • Média ≥2.000 ms: atenção; ≥4.000 ms: crítico, com ≥100 chamadas. Regra de regressão: média ≥2× a mediana de pelo menos três médias diárias anteriores positivas.
  • Recorrência contextual: pelo menos três dias anteriores com erro ≥5% e ≥100 chamadas/dia. Não é prova de causa crônica nem SLA violado.

Tempo e intervalos

O UTC da aquisição é autoritativo para nossa observação. Para dia analítico, usa-se HTTP Date em America/Sao_Paulo, ou instante da coleta se Date não for interpretável; essa convenção não comprova o fuso de agregação do banco. requestTime bruto é preservado, e desvio absoluto >900 s gera flag. Dias anteriores são rotulados D−n, sem fabricar observações passadas.

Delta só existe entre duas observações da mesma entidade, mesmo dia e fontes completas. Contadores devem ser válidos e não decrescentes; erro/rejeição delta não pode exceder chamadas delta. Reporte idêntico não gera tráfego intervalar. Diminuição é reset/revisão; mudança de dia suspende comparação. Não há média intervalar ou p95 inferidos.

Máquina de estados de incidentes

  1. Uma regra detectada abre ocorrência provisória; segunda detecção consecutiva confirma persistência.
  2. Coleta falha na primeira: atenção; segunda falha consecutiva: crítico. Isso é falha da observação Admin, não indisponibilidade comprovada de todos os serviços.
  3. Amostra avaliável abaixo do limiar inicia recuperação. Duas amostras avaliáveis consecutivas resolvem.
  4. Origem incompleta, métrica inválida, tráfego insuficiente ou revisão/reset não resolvem incidentes de serviço. Amostra não avaliável interrompe sequência de recuperação.
  5. Nova detecção durante recuperação reabre o estado ativo e zera recuperação. Após resolução, outra detecção gera nova ocorrência com ID próprio.
  6. Mesmo endpoint ausente de reporte completo não é automaticamente “saudável”; ocorrência persiste sem avaliação até haver nova evidência.

Qualidade

Flags cobrem horário inválido/divergente, arrays anteriores incompatíveis, contadores inválidos, erro/rejeição acima de chamadas, uptime inválido, uptime 100% com downtime positivo, uptime zero sem tráfego, média zero com tráfego e TPS médio acima do pico. São indícios de inconsistência; não reescrevemos valores para esconder o problema.

07 / MANUAL DO DASHBOARD

Do panorama ao detalhe.

O painel é uma página contínua. A barra lateral navega por âncoras e acompanha a seção visível; em telas menores, vira uma faixa horizontal. O seletor de reporte muda o recorte global.

1. Confira instante e cobertura

Leia a última coleta, idade, reportes com falha e o aviso de atraso. Após três horas sem coleta, o aviso muda no navegador, mesmo sem novo deploy. Valor antigo não vira volume atual.

2. Leia o panorama em conjunto

Fontes, chamadas, taxa de erro e média ponderada usam o ciclo completo. O ranking prioriza quantidade de erros. Clique numa fonte para filtrar; volte a “Todos” para recompor o escopo.

3. Priorize incidentes

Compare severidade, provisório/confirmado, evidência e amostras. Em recuperação ainda não é resolvido. Use o seletor para incluir resolvidos. Clique no endpoint para consultar histórico e fonte.

4. Explore tendências

Escolha taxa de erro, média ou chamadas do dia. Pontos têm horário e valor no tooltip. Linhas se interrompem em lacunas, atraso ou mudança de dia. Na primeira publicação há apenas uma observação própria.

5. Investigue endpoints

Busca e família afetam a tabela e o CSV, além do reporte global. Ordene por erro, taxa, média, chamadas ou nome. A tabela pagina 25 linhas. Detalhe abre em dialog acessível por teclado; Escape fecha.

6. Confronte coleta e qualidade

Compare HTTP/duração do Admin com média declarada do serviço. Consulte flags de contadores/paginação e estados de intervalo antes de concluir que houve melhora ou piora.

O detalhe de cada endpoint

Mostra instante, dia convencional, volume, taxa, média atual, mediana histórica de referência, deltas válidos, curva de erro observada, gráficos de erro e média dos dias anteriores, tabela D−1…D−7 declarada, flags, URL, SHA-256, caminho JSON, requestTime, uptime, downtime e TPS. A URL do serviço é evidência textual, não um botão que dispara testes de serviços de cliente.

Exportar e compartilhar

“Exportar endpoints” gera CSV em UTF-8 com BOM, separador ponto-e-vírgula, todas as linhas do filtro e campos de evidência. Valores com prefixos de fórmula são neutralizados. O botão exporta o contexto selecionado, inclusive métricas antigas identificadas por fresh/source_complete. Para compartilhar o manual, basta este HTML: estilos, scripts e os três diagramas SVG estão embutidos. A impressão oculta a navegação; abra blocos de código antes de imprimir caso queira incluí-los.

Cores têm rótulo textual: verde = coleta conciliada; âmbar = atenção/provisório/contexto antigo; vermelho = crítico; cinza = neutro/indisponível. “Sem sinais acima do limiar” depende das fontes e regras observáveis; não comprova ausência de problemas.

09 / OPERAÇÃO E RECUPERAÇÃO

Atualização remota com estado recuperável.

Execução local

python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.lock
.venv/Scripts/python.exe -m pip install --no-deps -e .
.venv/Scripts/python.exe -m admin_metrics.cli collect
.venv/Scripts/python.exe -m http.server 8766 --bind 127.0.0.1 --directory site

Abra http://127.0.0.1:8766. Linux/macOS: use .venv/bin/python. build no lugar de collect republica o estado sem nova amostra. Parâmetros: --root data --output site --config config. Não execute escritores simultâneos no mesmo root. O lock abandonado exige verificar o processo antes de removê-lo manualmente.

Acionamento no GitHub

Actions → “Monitorar Admin e publicar Pages” → Run workflow. refresh_data=true consulta fontes, atualiza histórico e publica. Desmarcado, republica o estado aprovado. Push em main executa testes e republica sem coletar; se ainda não houver estado, o bootstrap coleta. O cron é 17 */2 * * * UTC, a cada duas horas; por exemplo, 00:17 UTC corresponde a 21:17 do dia anterior em Brasília.

Agendamentos dependem da plataforma: podem atrasar, e repos públicos inativos podem ter schedule desabilitado. Verifique Actions e a idade no painel. Consulte documentação oficial de schedule e cobrança GitHub Actions. Não usa runner de maior porte pago. DuckDB roda no mesmo processo Python, sem máquina ou licença adicional contratada pelo projeto.

Retenção e integridade

Cada pacote state-<run> contém state.json, manifest.json e bronze atual/anterior, acompanhado de SHA256SUMS. Restore verifica checksum externo, hashes internos, referências recentes, nomes permitidos, duplicatas e limites de expansão; não extrai caminhos arbitrários. Uma falha de download/integridade bloqueia o ETL, em vez de iniciar histórico vazio. Releases aprovadas são ordenadas pelo instante de publicação; após confirmar a nova, conservar só as duas mais recentes desse prefixo.

Procedimento de recuperação

  1. Consulte o run do Actions, logs e ID publicado no rodapé/dashboard.json. Identifique se a falha foi coleta, build, upload, deploy ou promoção.
  2. Falha de coleta é um dado: execute novamente com refresh. Últimas métricas boas continuam como contexto antigo.
  3. Se o estado atual estiver corrompido, baixe explicitamente o pacote aprovado anterior e SHA256SUMS; use python scripts/cloud_pipeline.py restore --tag state-… em diretório de dados vazio. O comando não troca automaticamente o atual remoto.
  4. Depois de validar, use build para revisar o artefato. Corrija o estado remoto somente com ação explícita/revisada e evidência da restauração; não apague o anterior antes da confirmação.
  5. Deploy bem-sucedido com candidato ainda draft: verifique no Actions o job deploy e o dashboard.json publicado correspondendo ao manifest run_id. Então confirme com python scripts/cloud_pipeline.py promote --tag state-…. O comando exige o recibo de deploy criado somente após sucesso do job.
  6. Workflow interrompido antes do deploy: o draft não é considerado estado aprovado. Após verificar que não há execução ativa, remova o candidato residual; novas execuções não o usam no restore.

Verificações de desenvolvimento

.venv/Scripts/python.exe -m pytest -q
node --check src/admin_metrics/web/app.js

O CI roda Windows/Linux com Python 3.11/3.12. O workflow de publicação também testa antes de coletar. Mudanças em regras exigem revisar comparabilidade histórica; o estado existente não é recalculado silenciosamente com os novos limiares.

@@EVIDENCE@@

Na conferência inicial, o Santander principal trouxe 112 identidades na primeira página, declarou totalPages=2 e repetiu as identidades em uma segunda consulta independente. O coletor de produção encerra assim que cobre totalRecords e registra a divergência de metadata. Também foi observada diferença próxima de três horas entre requestTime e Date; isso é uma divergência observada, sem correção global presumida.

Limitações e leituras que não são permitidas

  • Não há medição sintética direta de todos os serviços, nem prova de disponibilidade contínua a partir de coletas a cada duas horas.
  • Não existe detalhamento por status de erro no contrato. Rejeição não prova 429; 403 do Admin não identifica sua causa nem prova falha dos serviços.
  • Média não é p95. Os limiares configurados não são classificação regulatória.
  • Ausência de endpoint no reporte não prova ausência de oferta. Identidades e cobertura podem mudar entre ciclos.
  • Dias parciais, janelas e semântica de consolidação dependem da origem. Não inferimos janela fixa a partir de um reporte vazio.
  • Contagens entre reportes são agregados operacionais, sem deduplicação de transações entre instituições.
  • Bronze antigo expira: hashes de observações antigas continuam disponíveis, mas reprocessamento integral de mais de dois ciclos exige retenção adicional.
  • Single node, um escritor, sem autenticação corporativa. Dados e documentação são públicos.
